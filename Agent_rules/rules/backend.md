# 后端使用约束

以下为后续实现约束；现有代码未满足的部分应按需求补齐。

## 技术与分层

- 使用现有 Python、FastAPI、Pydantic、SQLAlchemy 技术栈。更换框架或新增依赖必须有具体需求依据，并记录依赖及安装方式。
- `main.py` 负责创建应用与注册路由；`api/` 负责 HTTP、参数校验、响应模型和错误转换。
- `application/` 组织业务流程与事务，通过 `UnitOfWork` 和 `PasswordHasher` 接口访问外部能力。
- `domain/` 保存领域实体、业务规则和仓储接口，不依赖 FastAPI 或 SQLAlchemy。
- `infrastructure/` 实现仓储、数据库、工作单元与密码哈希；依赖在 `api/dependencies.py` 组装。
- 不在路由中直接执行 SQL、计算命中率或提交数据库事务。

## 登录与数据归属

- 沿用 `/auth/login`、`/auth/me`、`/auth/logout` 的 Cookie 会话方式。
- 密码使用 Argon2 哈希；数据库不保存明文密码。响应不返回密码或密码哈希。
- 原始令牌只用于客户端 Cookie；数据库保存 SHA3-256 摘要和过期时间。会话有效期保持 7 天，与 Cookie 一致。
- Cookie 保持 HttpOnly、Path=/、SameSite=Lax；本地 HTTP 的 `COOKIE_SECURE` 默认 false，部署 HTTPS 时设置 `COOKIE_SECURE=true`。登录与删除 Cookie 属性一致；认证响应使用 `Cache-Control: no-store`。生产 HTTPS 尚未实测。
- 训练接口必须验证登录状态和训练归属。客户端传入的 `user_id` 或 `session_id` 不能作为授权依据。
- 用户身份由有效会话确定；保留带 `user_id` 的接口时，必须校验它与当前用户一致。
- 当前训练路由尚未实施上述身份和归属校验。

## 业务与接口

- 请求和响应使用 `api/schemas/` 中的模型；投篮区域沿用 `ShootingZone`。
- 已结束训练禁止新增投篮；重复结束保留第一次结束时间。
- 投篮组提供创建和结束操作，不新增给已有组追加或修改投篮的接口；已结束组禁止添加投篮。`finish_shot_group(group_id, zone, attempts, made)` 使用严格整数校验，要求 attempts > 0 且 0 <= made <= attempts。创建空组允许 zone=None；首次结束必须选择有效点位，先设置点位再生成逐球记录并结束；相同点位和数量重试返回原组，已结束组修改点位或数量被拒绝，仓储在首次结束时保存完整组内记录和结束时间，已结束组不覆盖原数据。
- 统计复用 `domain/shooting/rules.py`；API 命中率为 0～1，多场统计按全部投篮累计计算。
- 无训练返回空列表，无投篮返回零统计；不存在的资源与无数据状态应明确区分。
- 错误按实际原因转换为 HTTP 状态：未登录/会话失效 401，权限不足 403，资源不存在 404，重复用户名 409。不要把数据库异常统一包装为密码错误。
- 修改现有 API 字段或路径时同步更新前端和项目架构文档。

## 事务与验证

- 服务在 `with self.uow` 中操作仓储，并显式调用 `commit()`；仓储不自行提交。
- 工作单元退出时回滚未提交操作并关闭 Session；异常不得吞掉。
- 当前测试文件按用户要求忽略，不作为接口契约或行为依据。验证应以需求、当前实现与实际检查结果为准，未执行的检查不能声称通过。
- 后端版本要求和依赖清单尚未明确；需要建立可复现安装流程时再补充，不猜测版本。
